# Phase 0 Research: Honouring locally-confirmable SDP QoS preconditions

Deferred in specs/045-long-tail-conformance (research.md Decision 1) as
needing "new SDP-level QoS attribute parsing and a bearer-readiness state
machine." Two Explore passes (current `Require`-gate/SDP-parser code;
RFC 3312's actual normative text, fetched directly rather than recalled)
plus the two rounds of `/speckit-clarify` resolved this into a bounded
feature.

## Decision 1: The offer's `remote` status type — not `local` — is this bridge's own segment

**Decision**: This bridge confirms the offer's `remote`-status-type lines
in its answer (tagged `local`, per the required inversion); it never
invents a status for the offer's `local`-status-type lines (mirrored
through, tagged `remote`, in the answer).

**Rationale**: RFC 3312 §4 is explicit and was verified against the actual
RFC text (not recalled from memory, after the first spec draft had this
backwards):

> "The values of the tags 'send', 'recv', 'local' and 'remote' represent
> the point of view of the entity generating the SDP description. In an
> offer, 'send' is the direction offerer->answerer and 'local' is the
> offerer's access network. In an answer, 'send' is the direction
> answerer->offerer and 'local' is the answerer's access network."

And §5.2: "an answer MUST be generated ... taking into account that
'send', 'recv', 'local' and 'remote' tags have to be inverted in the
answer."

So in the INVITE's offer (generated by the caller), `local` names the
*caller's* own segment and `remote` names what the caller believes about
*this bridge's* segment. This bridge can only ever honestly confirm its
own segment — which is the offer's `remote` lines, inverted to `local` in
the answer. The offer's `local` lines are the caller's own claim about
itself; this bridge has no basis to assert anything about them beyond
mirroring the offerer's own `a=curr:qos local` value through as
`a=curr:qos remote` in the answer, unaltered.

Getting this backwards (as the initial spec draft did, before the RFC text
was actually fetched) would have meant fabricating a "confirmed" status
for the *caller's* segment — a live protocol falsehood, not merely an
unsupported feature — which is exactly the failure mode this feature
exists to avoid (same discipline already applied to SMS-07: don't ship a
table/mapping from memory without a verifiable primary source).

## Decision 2: `e2e` cannot be unilaterally confirmed; `mandatory` strength there stays declined

**Decision**: An `a=des:qos` line naming `e2e` at `mandatory` strength
still declines the whole call (confirmed via `/speckit-clarify`). `e2e` at
`optional` strength does not block the call — the answer reports it
not-yet-met and the offerer, per RFC 3312, is required to tolerate that
for optional strength.

**Rationale**: `e2e` status is not relative (it means the combined,
whole-path resource, not either endpoint's segment alone) and RFC 3312's
whole reason for a segmented model is that neither endpoint can attest to
the other's segment on its own. Confirming it truthfully requires learning
the offerer's own segment status via a mid-dialog exchange (RFC 3312's own
examples use `UPDATE`, optionally carried reliably via `100rel`/`PRACK`).
Both are genuinely absent from this codebase by deliberate prior decision
(`SUPPORTED_EXTENSIONS` is empty; `UPDATE` is an explicitly-unimplemented
method) — building either is a materially larger, currently unjustified
subsystem for a header no carrier reachable here has ever sent live. See
Decision 4 (response code) for how the decline is now more specific than
before this feature.

## Decision 3: Header-level gate — `precondition` moves from "always refused" to "genuinely (partially) supported"

**Decision**: Add `"precondition"` to `SUPPORTED_EXTENSIONS`
(`gsm-sip-bridge/src/ims/agent/mod.rs:398`). The pre-SDP-parse blanket
`420` in `unsupported_required_extensions` no longer fires for
`Require: precondition` on its own; the accept/decline decision moves to
after the offer is parsed, decided by the offer's actual `a=des:qos`
content (Decisions 1-2).

**Rationale**: `SUPPORTED_EXTENSIONS`'s own doc comment already states the
list is "grown only by growing the UAS" — this is precisely that: unlike
`timer`/`100rel`/`replaces`/`gruu`/`path` (each still empty-list, since
none has real behavior behind it — MT-10), this feature adds a bounded but
real capability behind `precondition`. Advertising `Supported:
precondition` in this bridge's own responses (the list's second use,
`inbound.rs`'s `UAS_EXTRA_HEADERS`) is now honest: the bridge genuinely
implements a real subset of the extension, the same way it's honest to
advertise `Supported: 100rel` would be dishonest today (MT-04's finding)
because zero of that extension exists.

**Where the content-level check lives**: parallel to SDP-03's existing
transport-profile check in `agent::inbound::handle_invite`
(`gsm-sip-bridge/src/ims/agent/inbound.rs`, right after
`sdp::parse_offer(&req.body)?` succeeds, before the codec precheck) — a
new check reads the parsed offer's precondition lines and declines only if
an `e2e`-`mandatory` line is present, mirroring the existing
transport-profile-decline shape (compute a verdict from the parsed offer,
early-return `Ok(None)` with a decline response on failure).

## Decision 4: The content-level decline uses `580 Precondition Failure`, not `420`

**Decision**: When the offer's SDP content itself is what triggers a
decline (an `e2e`-`mandatory` line this bridge cannot confirm), the
response is `580 (Precondition Failure)` — the response RFC 3312 §6.2
defines for exactly this situation — not `420 Bad Extension`.

**Rationale**: `420` means "the UAS does not implement this `Require`
extension at all" (RFC 3261 §8.2.2.3) — no longer true once `precondition`
is in `SUPPORTED_EXTENSIONS` (Decision 3): the extension genuinely is
implemented, just not every offer shape it can express. RFC 3312 §6.2
covers this precisely: "If a UAS determines that it is not capable of, or
is not willing to support, one or more mandatory preconditions requested
by the offerer, it MUST reject the offer with a 580 (Precondition
Failure) response." Matches this codebase's stated principle throughout
the conformance work (batches 1-8): a response should say what actually
happened, not the closest available generic code. No SDP body needed on
the decline (RFC 3312 §6.2 makes an `a=curr` body optional on the
failure response) — kept header-only, matching the existing minimal style
of `build_420_bad_extension`/`build_488_not_acceptable`/
`build_488_incompatible_transport`/`build_415_unsupported_media`, all of
which are header-only declines with no body.

## Decision 5: Interaction with SDP-04 (offerless INVITE) is a natural no-op

**Decision**: No special-case code is needed for the offerless-INVITE
path (specs/047-offerless-invite-sms-reassembly).

**Rationale**: `handle_invite` already branches to
`handle_offerless_invite` before `sdp::parse_offer` is ever called, when
`req.body` is empty. An offerless INVITE therefore has zero `a=des:qos`
lines by construction — which FR-007 already defines as "no precondition
requested." If a carrier ever sent `Require: precondition` on a genuinely
offerless INVITE, it would fall through Decision 3's gate (now supported)
and Decision 1-2's per-line logic would simply find nothing to act on —
proceeding exactly as SDP-04's existing flow does today, no new branch
required.

## Decision 6: RFC 3312 wire syntax — exact ABNF, confirmed against the RFC text

```text
des-qos-line   =  "a=des:qos" SP strength-tag SP status-type SP direction-tag
curr-qos-line  =  "a=curr:qos" SP status-type SP direction-tag
conf-qos-line  =  "a=conf:qos" SP status-type SP direction-tag

strength-tag   =  "mandatory" / "optional" / "none" / "failure" / "unknown"
status-type    =  "e2e" / "local" / "remote"
direction-tag  =  "none" / "send" / "recv" / "sendrecv"
```

`direction-tag` means different things on `a=des` versus `a=curr`/`a=conf`:
on `a=des` it names which direction(s) of the media stream the *desired*
precondition strength applies to (mirrors the SDP media-direction concept
specs/043 already models as `MediaDirection`); on `a=curr`/`a=conf` it is a
*status* value — how much of the resource is currently/confirmed ready
(`none` = not met, `sendrecv` = fully met, `send`/`recv` = partially met)
— not a media direction, despite reusing the same four tokens. The two
must not be conflated in code or naming; see `data-model.md`'s
`QosStatus` vs. `QosDesired` split.

**Correction (PR #68 Greptile review, round 2)**: `send`/`recv` invert
between offer and answer exactly like `local`/`remote` — Decision 1's own
quoted RFC 3312 §4 text already says so ("the tags 'send', 'recv',
'local' and 'remote' represent the point of view of the entity
generating the SDP description"), but the first implementation of this
feature only applied that inversion to the status-type, carrying the
direction token straight through unswapped. `sdp::invert_qos_direction`
now applies the same `send`↔`recv` swap (`sendrecv`/`none` are
direction-symmetric and pass through unchanged) everywhere an
offer-relative direction crosses into the answer — the `Remote`/`E2e`
branches of `precondition_verdict` and the offerer's-own-segment
mirroring loop alike. A second instance of the same lesson Decision 1
already recorded once: a quoted primary source doesn't help if only half
of what it says gets applied.
